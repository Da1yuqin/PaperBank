# StrongResponse · 审稿回复

按原问题作答。第一句给答案，随后给证据、解释与位置。完整模板见 [rules.md](references/rules.md)，起草与检查提示词见 [prompts.md](references/prompts.md)。

## 回复格式

这是默认交付格式；提交时按当轮平台要求调整。

- 每位审稿人单独一个 Markdown 代码块。代码块用于复制，提交时粘贴其中正文。
- 从第一个问题开始：`> **Q1.1: [忠于原意的问题标题]**`。保留 blockquote、加粗、编号和冒号，不加 `Dear Reviewer`。
- 一个大问题有多个子问题，拆成 `Q1.1a`、`Q1.1b`；保留原问题与编号的对应关系，不改写成更容易回答的问题。
- 题目下第一句直接答。真正的是否题可用 `Yes.` 或 `No.`；证据不足则明确不能判断。为什么、怎样、数值题分别先给理由、操作、具体值。观点性质疑先给相关结论，不硬改成是否题。
- 再写必要设置、证据及其含义，给表号、节号或行号。流程问题写清输入、操作与输出。
- 列点使用 `**Evidence**: ...` 这类短标签。数据比较适合表格时用紧凑表格，保留比较条件、单位、指标方向与样本范围，不在正文复述每个数值。
- 不用致谢、背景或复述问题占第一句。每问处理一个关切，问题之间空一行；简短致谢放回复末尾，不请求提分。

## 起草顺序

1. 读取论文、完整 review、当前回复与已有结果；按审稿人提取 Weaknesses、Questions、建议及评分理由里的每个具体关切。
2. 建立「原问题 → 所需证据 → 已有依据与位置 → 缺口」。一句话有多问就拆开；不推测审稿人的身份、能力或动机。
3. 根据问题选择回应：定义给定义，流程给案例，效果给对照，替代解释给能区分两种解释的检验。设计理由不能代替效果证据。
4. 已有结果能回答就直接整理；缺关键证据时说明缺口和最小对照，由作者决定是否补实验。合理批评修正，有分歧给依据，无法区分就缩小主张。
5. 先回答再给证据与位置。首句结论、证据范围与论文主张必须一致；不能把相关性写成因果，也不能从一个设置外推所有场景。

## Revise loop

以原 review 的问题清单为准，不能按当前回复的目录检查：

| 原问题 | 回复位置 | 是否答到 | 证据是否匹配 | 剩余疑问 | 最小改法／缺失证据 |
| :--- | :--- | :--- | :--- | :--- | :--- |

先修漏答、证据和逻辑，再缩文字、调语气。只改未通过项，改后重查同一张清单；新证据带来新疑问时补入清单。

每问有明确回应，事实有来源，证据与结论对应，格式和篇幅符合当轮规定后停止。无法补齐的证据交作者决定，不编结果，不靠模拟预测评分或接收。

## 追问与 AC 总结

追问先定位尚未解决的关切，不重复粘贴上一轮整篇回复。AC 总结按「关键问题 → 作者回应 → 证据位置 → 剩余分歧」组织；只引用真实评审原话，不推测尚未回应的审稿人态度，不给 AC 下指令。

## 材料与交付

核对当轮字数、匿名、补实验、链接、修订稿和 AI 使用规定；确认材料可在所选工具中使用。不编造结果、引用、评价或已完成修改，不隐藏影响结论的条件、不利结果与错误。

只改获授权的回复文件，保留原 review、原始记录及他人修改。补实验、改稿和提交分别依作者授权。英文回复可附中文供作者审阅，内部缺口与检查记录不混入提交文本。
